01

Pause a real tool request

canUseTool receives the actual tool name, input and callback context. The SDK waits on a promise while the browser shows the request. No approval is granted merely because the dialog is visible.

02

Approve or edit before execution

Approve once returns the original input. Approve with changes rewrites the output to reviewed.txt and uses the student-edited content. Independent host checks show what the actual Write created.

03

Remember within the current session

Inspect actual SDK suggestions and the proposed session-scoped updates. Remember returns eligible acceptEdits or Write rule updates through updatedPermissions. Compare two writes with one remembered approval against approving each write once.

04

Reject, suggest or redirect

A rejection message reaches the model as tool feedback. A suggestion guides it to read the lesson instead. Redirect blocks the current write and sends a separate user instruction on the same live Query after the current turn ends.

05

Build the browser approval round trip

The server streams SSE data frames to the browser; POST /api/approve resolves one pending request ID. The dialog displays tool-specific input, toolUseID, deadline and whether the output existed before review.

06

Handle cancellation and earlier approval

Abort or timeout resolves and removes pending requests. Stale decisions cannot be replayed. Pre-approved Write calls never reach the callback. The terminal example uses the same y/n decision shape for a bounded create/delete exercise.
